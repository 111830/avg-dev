# The C++ Compilation Model and Modern Modules

A comprehensive guide to understanding how C++ code is transformed into an executable, covering the traditional compilation stages and the modern C++20/23 Modules system.

---

## 1. The 4 Stages of Compilation
Every C++ program passes through these four distinct phases.

### Phase 1: Preprocessing
* **What it does:** Handles directives starting with `#` (e.g., `#include`, `#define`). It physically copies header file contents into your source file and expands macros.
* **Input:** Source Code (`.cpp`)
* **Output:** Translation Unit (Expanded source code).

### Phase 2: Compilation
* **What it does:** Translates the C++ code into **Assembly Language** (low-level text instructions specific to the CPU architecture). Checks for syntax errors and optimizes logic.
* **Input:** Translation Unit
* **Output:** Assembly Code (`.s`).

### Phase 3: Assembly
* **What it does:** Translates the Assembly text into **Machine Code** (Binary 0s and 1s).
* **Input:** Assembly Code (`.s`)
* **Output:** Object File (`.o` or `.obj`).

### Phase 4: Linking
* **What it does:** Combines your Object Files (`.o`) with System Libraries. It connects function calls (like `std::cout`) to their actual memory addresses in the binary libraries.
* **Input:** Object Files + Static/Shared Libraries (`.so`, `.a`, `.dll`)
* **Output:** Executable File (`a.out`, `.exe`).

---

## 2. Modern C++ Modules (Concepts)

With C++20/23, the compilation model changes slightly to improve build speeds and structure.

### Key Concept: Two-Phase Compilation (Clang)
Unlike traditional headers, Modules are often compiled in two steps:
1.  **Interface Generation (`--precompile`):** Creates a `.pcm` file. This is a binary "map" or description of the module (AST). It is NOT executable code.
2.  **Object Generation (`-c`):** Creates a `.o` file. This is the actual executable machine code derived from the module.

### File Extensions Legend
* **`.cppm`**: Module Interface Unit (Source code where you `export module ...`).
* **`.pcm`**: Precompiled Module (The "Map" for the compiler).
* **`.o`**: Object File (The "Code" for the linker/CPU).
* **`gcm.cache`**: A directory used by GCC to automatically store module maps.

## 3. Workflow Diagrams

### Scenario A: User-Created Named Modules (e.g., `math.cppm`)

#### 🔵 CLANG (Explicit / The "Open" Way)
*Phases are separated: First build the map (`.pcm`), then build the code (`.o`).*

```text
    Phase 1 & 2 (Analysis)           Phase 3 (Code Gen)             Phase 4 (Linking)
---------------------------      ---------------------          -----------------------

[ math.cppm ]                    [ math.pcm ]
      |                                |
      | ( --precompile )               | ( -c )
      v                                v
[ math.pcm ] ------------------> [ math.o ] ------------------+
(Interface / Map)                (Machine Code)               |
                                                              |
                                                              v
                                                         [  main  ]  <-- (Final Program)
                                                              ^
                                                              |
[ main.cpp ] -------------------------------------------------+
(Needs the .pcm to understand imports)
```

#### 🟢 GCC (Implicit / The "Automatic" Way)
*Phases are combined: `-c` generates the code and hides the map in a cache folder.*

```text
       Phases 1, 2 & 3 (Combined)                                Phase 4 (Linking)
-----------------------------------------------              -----------------------

[ math.cppm ]
      |
      | ( -c )
      |
      +-----> [ gcm.cache/ ] (Hidden Map)
      |       (GCC stores it automatically)
      |
      v                                                       +----------+
[ math.o ] -------------------------------------------------> |   main   |
(Machine Code)                                                +----------+
                                                                    ^
                                                                    |
[ main.cpp ] -------------------------------------------------------+
(Finds the map in gcm.cache automatically)
```

### Scenario B: Header Units (Legacy Support)
*Converting old `<iostream>` into a module.*

#### 🔵 CLANG (Header Units)
*You create the Map (`.pcm`), but the Machine Code exists in the System Library.*

```text
      System Source                     Your Compiler
---------------------------      ---------------------------

[ <iostream> ] (Header file)
      |
      | ( --precompile )
      | "Scanning"
      v
[ iostream.pcm ] ---------------------+
(Binary Map)                          |
                                      | (Reads Map)
                                      v
[ main.cpp ] ------------------> [ main.o ]
(Your Code)                           |
                                      | (Linking)
                                      v
                                 [  main  ] <=== [ libc++.so ]
                                                 (System Library
                                                  containing the code)
```

#### 🟢 GCC (Header Units)
*GCC converts the header and hides it in the cache.*

```text
      System Source                     Your Compiler
---------------------------      ---------------------------------

[ <iostream> ] (Header file)
      |
      | ( -x c++-system-header )
      | "Conversion"
      v
[ gcm.cache/... ] <-------------------+
(Hidden Map)                          |
                                      | (Finds Map automatically)
                                      |
[ main.cpp ] ------------------> [ main.o ]
                                      |
                                      | (Linking)
                                      v
                                 [  main  ] <=== [ libstdc++.so ]
```

## 4. Command Cheat Sheet

Here are the commands for the three different ways to structure a C++ project.

### Method 1: The Classic Way (Standard Legacy)
* **Code uses:** `#include <iostream>`
* **Scenario:** The traditional way. No modules, just textual inclusion.
* **Compiler:** Works identically on GCC and Clang.

```bash
# Compile and Link in one step
g++ -std=c++23 main.cpp -o main

# OR for Clang
clang++ -std=c++23 main.cpp -o main
```

### Method 2: Header Units (The "Bridge")
* **Code uses:** `import <iostream>;` (Notice the angle brackets `< >`)
* **Scenario:** Treating old headers as modules.
* **Compiler:** Best demonstrated with **GCC**.

```bash
# 1. Precompile the System Header (Once)
# -x c++-system-header tells the compiler this is a header, not a file
g++ -std=c++23 -fmodules-ts -x c++-system-header iostream

# 2. Compile Your User Module (math.cppm -> math.o)
g++ -std=c++23 -fmodules-ts -c math.cppm -o math.o

# 3. Compile Main and Link Everything
g++ -std=c++23 -fmodules-ts main.cpp math.o -o main
```

### Method 3: Named Modules (The Modern Future)
* **Code uses:** `import std;` (No brackets, just the name `std`)
* **Scenario:** Using the true C++23 Standard Library Module.
* **Compiler:** Best demonstrated with **CLANG-18** (Explicit Build).

```bash
# 1. Build Standard Library Module (std.pcm) - DO THIS ONCE
# Converts the raw library source into a binary map
clang++-18 -std=c++23 -stdlib=libc++ -Wno-reserved-module-identifier --precompile -o std.pcm /usr/lib/llvm-18/share/libc++/v1/std.cppm

# 2. Build User Module Interface (math.pcm)
# Creates the map for your module, using std.pcm
clang++-18 -std=c++23 -stdlib=libc++ -fmodule-file=std=std.pcm --precompile math.cppm -o math.pcm

# 3. Build User Module Object (math.o)
# Converts the map into machine code
clang++-18 -std=c++23 -stdlib=libc++ -c math.pcm -o math.o

# 4. Link Everything (Main + Maps + Objects)
# Connects Main, the Maps (for reading), and the Objects (for execution)
clang++-18 -std=c++23 -stdlib=libc++ -fmodule-file=std=std.pcm -fmodule-file=math=math.pcm std.pcm math.o main.cpp -o main
```
